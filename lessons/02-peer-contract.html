RaceBench - Lesson 2

peer_contract: coordination by stated intent

The baseline strategies mostly compare files, text, symbols, or read sets. peer_contract adds a more semantic move: agents declare what they intend to change, then overlapping writes wait for affected peers to ACK or reject the contract.

One sentence version. peer_contract is voluntary, mediated negotiation: agents call declare_intent, peers answer with ack_contract, and the harness blocks overlapping writes until compatible peers ACK.

Why This Is An Extension

The baseline strategies ask questions like: "Is this the same file?", "Can Git merge these lines?", "Which AST symbol changed?", or "Who read this symbol?" Those are structural questions. peer_contract asks a different question: "Can one final implementation satisfy both agents' subtasks?" That is closer to how engineers coordinate interface changes.

Not just a lock

A lock says "wait because the scope overlaps." A contract can say "go ahead, but preserve this exported interface."

Not just notify

A notification warns after a write lands. A contract can stop an overlapping write before it lands unless peers ACK.

Not full A2A autonomy

The agents provide intent and judgment, but the RaceBench harness detects overlap, delivers requests, waits, and enforces timeouts.

The Protocol

1. DeclareAn agent calls declare_intent with path, expected symbols, summary, exports, and must-preserve constraints.
2. DetectThe harness checks whether active peers read or declared overlapping work in the same file or symbol scope.
3. ProposeIf overlap exists, peers receive a contract request in their notification mailbox.
4. ACK or ConflictA peer calls ack_contract with ack if one final implementation can satisfy both subtasks, or conflict if the requirements cannot coexist.
5. Gate WriteThe overlapping write proceeds only after required active peers ACK. A conflict rejects the write. No answer before timeout returns lock_timeout.

What Counts As Overlap?

The implementation tracks each agent's read set and declared intents. On write, it computes changed top-level symbols using the same AST symbol machinery as the baseline strategies. A peer is required when:

CaseEffect
Same file, disjoint declared symbolsNo ACK needed. Benign overlap can proceed.
Same file, same declared symbolACK needed before write.
Peer read the affected symbolACK needed because the peer may be planning from stale state.
Symbols unspecified or file-level fallbackTreated conservatively as overlapping.

The Key Concept: Contract

In software engineering, a contract usually names obligations between a provider and a client: what must be true before use, what is guaranteed afterward, and what must remain invariant. That tradition is associated with Bertrand Meyer's Design by Contract. RaceBench uses the idea more loosely: a peer contract is not executable verification; it is a compact, negotiated statement of compatibility between agents.

exports

Names or interfaces other agents may rely on, such as fetch or DEFAULTS.timeout.

must preserve

Behavior, signatures, or invariants that should survive the final implementation.

ack

A peer says: "My task can still succeed if this intent is respected."

What It Saves, What It Misses

StrengthWhy it matters
Prevents some stale overwritesOverlapping writes wait before landing, unlike notify.
Preserves benign parallelismDeclared disjoint symbols avoid file_lock's false-positive stalls.
Captures semantic constraintsAgents can say "keep this API stable," which AST/text merge cannot infer reliably.
WeaknessFailure mode
Voluntary declarationIf an agent does not declare intent, the harness can infer only a thinner write intent at write time.
LLM judgmentA peer can ACK something it misunderstood, so compatibility is not mechanically proven.
No persistent obligation enforcement yetThe plan notes future work to carry obligations after ACK; the current V1 mainly gates writes.
Same-file/symbol centeredCross-file dependency overlap is listed as future work for smarter intent scope.

Try It

Agent A wants to change api.py::fetch to add timeout. Agent B wants to change the same function to add retries. One final implementation could support both optional parameters. What should B answer when A's contract request arrives?
